- **Scheduled alert check in the server** (QV-639, internal until alerts ship in QV-592):
  `trailbeam.server.alerts_run` runs the hosted app's alert check: for each workspace with a rule and an alert
  channel it evaluates every dashboard rule and "Alert me" rule, records the state and hands the changes to delivery.
  A failing workspace is recorded with its error and doesn't stop the others; a lease per workspace keeps two checks
  from overlapping; the workspaces checked longest ago go first, within a time budget; a muted or snoozed rule records
  its state, sends nothing and sends one "still firing" change when it wakes; an ignored cause holds its rule.
  `trailbeam.server.alerts_scheduler` runs it every few minutes on a thread inside the server
  (`TRAILBEAM_ALERT_CHECK`: minutes, `on` or `off`; off by default for now). Nothing starts it yet: the alert
  tables and API come later in QV-592. The decisions are held to shared cases in `contract/fixtures/alerts-run.json`.
