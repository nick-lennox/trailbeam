- **S3 uploads are recorded and joined to the SQS messages their bucket notifications sent** (QV-511; contract
  revision 3.7, section 27). The Python hooks (boto3 `s3` clients, with `trailbeam.boto.install()`) and the Node.js
  hooks (an `S3Client` passed to `instrument`) emit one `trailbeam s3_upload` span per `PutObject`,
  `CompleteMultipartUpload` or `CopyObject` call, ok or failed, with the bucket, the returned `ETag` and `VersionId`,
  and the error code of a failed call. The object key is recorded only when body capture is on for the bucket (its
  name or `*` in the body capture list); contents, user metadata and `CopySource` never are. Trailbeam joins an upload
  to a receive by bucket, object key and event time, so only where both the uploader and the receiving queue capture
  bodies, and only when exactly one recorded upload of the key fits. The message's timeline then starts with an
  observed "Uploaded to S3 bucket" step, with the other SQS messages the upload reached and the S3 delivery time
  (`SentTimestamp` minus the record's `eventTime`), instead of the inferred "S3 ObjectCreated:…" step. Where body
  capture is off on either side, nothing is joined and the inferred step stays. `GET /api/messages/{id}` has a new
  `s3_upload` step type. Stores: SQLite schema 24 (two indexes), Postgres schema 18 (tables `s3_uploads` and
  `s3_receives`), both applied on start.
